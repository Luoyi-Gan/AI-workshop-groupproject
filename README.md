# AI Workshop Group Project — 四子棋 AI

一个以 **Python 搜索算法**为核心、通过**浏览器界面**展示的四子棋（Connect Four）小组项目。

我们希望回答的问题是：**在有限思考时间下，如何让 AI 下得更好？**

> 当前状态：项目规划阶段。本文描述计划中的功能、实验与交付物，尚未实现程序，也没有正式实验结果。小组共 6 人，具体人员分工待确定。

## 1. 作业要求与项目目标

课程涵盖 Minimax、Alpha-beta pruning、Negamax、SSS* 等搜索方法，以及 Tic-Tac-Toe、Connect Four、Hexapawn 等棋类游戏。

本项目计划通过四子棋满足以下要求：

| 作业要求 | 项目对应内容 |
| --- | --- |
| 至少 3 个递进的 AI 挑战等级 | 简单、中等、困难三档，通过对战实验验证差异 |
| H2M：交互式人机对战 | 玩家在网页上与指定难度的 AI 对战 |
| M2M：非交互式机器对战 | AI 自动完成整局对战，并支持无界面批量比赛 |
| 鼓励自设计算法击败经典方法 | 自设计威胁评估策略，与基础评估进行公平对比 |
| 漂亮的界面 | 棋盘交互、落子动画、胜利连线、搜索统计及棋谱回放 |
| Python 源码、PPT、原始数据和统计图表 | 统一整理为最终提交包 |

默认老师允许选择四子棋，并接受 Python 核心搭配网页界面；第一周核对这两点。

## 2. 技术路线与范围

| 层次 | 计划采用的技术 | 职责 |
| --- | --- | --- |
| 游戏引擎 | Python 3.11 | 棋盘、合法落子、轮次、胜负、平局与棋谱 |
| AI 引擎 | Python | 搜索、评估、思考预算与搜索统计 |
| 服务端 | FastAPI | 管理各局状态、校验操作、调用 AI、提供接口 |
| 网页界面 | 原生 HTML / CSS / JavaScript | 展示棋盘、处理操作、动画、统计与回放 |
| 实验系统 | Python 命令行脚本 | 生成开局、运行批量比赛、导出数据与图表 |

游戏引擎独立于网页。同一套游戏规则和 AI 同时服务人机对战、网页自动对战和命令行批量实验。

首版在本机启动，通过浏览器访问。范围包括完整四子棋、三档 AI、两种对战模式和实验系统；不加入账号、联网对战或模型训练。课程列举的算法作为学习背景，本项目重点实现 Minimax 和 Alpha-beta，暂不安排 SSS*。

### 公共接口约定

- 统一 AI 接口：`choose_move(state, config)`，返回落子列与搜索统计。
- 搜索统计至少包含：耗时、节点数、实际完成深度、评估值。
- 后端提供：创建游戏、读取状态、玩家落子、推进一次 AI 落子的接口。
- 后端负责判断操作是否合法、轮次是否正确、游戏是否结束；不同棋局的状态彼此独立。
- AI 搜索在工作进程执行，避免阻塞服务；重复操作和重开后返回的旧结果不能污染当前棋局。

具体数据结构与接口字段在第一周统一，之后各模块按约定并行开发。

## 3. 三档 AI 与改进策略

### 初始难度配置

| 难度 | 初始配置 | 预期表现 |
| --- | --- | --- |
| 简单 | Minimax，搜索 2 层，基础评估 | 能进行基本判断 |
| 中等 | Alpha-beta，搜索 4 层，同一基础评估 | 更深入地考虑双方回应 |
| 困难 | Alpha-beta + 迭代加深，最多 8 层，1.5 秒思考预算，改进评估 | 在预算内完成更强的决策 |

以上参数为初始值，依据实际性能与比赛结果在第五周正式实验前校准并冻结。困难档超时返回最后一次完整搜索的结果；所有档位都必须保证合法落子。

**难度等级与搜索方法需要分别验证。** 相同深度与评估函数下，Minimax 和 Alpha-beta 应得到相同的最优分数，剪枝主要提高效率。递进棋力来自更深入的搜索、评估能力和思考预算，不能仅凭算法名称判断强弱。

### 自设计改进：威胁感知评估

集中完成一项可解释、可测量的改进：

1. 区分可以立即完成四连的威胁，与受重力限制、暂时无法完成的威胁。
2. 识别双重威胁，即对手下一步难以同时封堵的两个获胜点。
3. 在独立调参局面上调整评估权重，再使用保留测试局面验证效果。
4. 为新增评估项提供独立开关，以便开展消融实验。

迭代加深、走法排序和置换表属于已有技术，使用时明确引用。项目贡献是评估策略的设计、实现和实验验证，不宣称发明全新的搜索算法。

## 7. 测试与实验方案

### 功能与正确性测试

- 横向、纵向、两种斜向四连获胜。
- 满列非法落子、平局、结束后禁止继续落子。
- AI 超时、连续点击、重开、独立棋局状态隔离。
- 自动机器对战能够完成并导出完整记录。
- 在小规模局面上，Minimax 与 Alpha-beta 在相同深度和评估函数下返回相同最优分数；如存在多个最优落子，允许选择不同的等价落子。

### 三类实验

| 实验 | 控制条件 | 回答的问题 |
| --- | --- | --- |
| 三档循环对战 | 使用相同开局，交换先后手，固定各档配置 | 难度是否确实递增？ |
| Minimax 对比 Alpha-beta | 同局面、同深度、同评估函数，确保搜索完成 | 剪枝节省多少节点和时间？ |
| 基础评估对比改进评估 | 同搜索引擎、同思考预算，分别关闭新增评估项 | 自设计改进是否有效？ |

### 对战规模与公平性

- 正式三档对战使用 **100 个保留开局**，每个开局交换双方 AI 的先后手。
- 每对档位进行 **200 局**，三组配对合计 **600 局**。
- 使用固定随机种子生成合法、未结束、去重的开局，保留完整落子序列。
- 调参集合与正式测试集合分开，正式结果使用冻结的配置。
- 记录 Python 与依赖版本、机器配置、算法参数及运行命令，保证实验可复现。

### 数据与验收

记录胜、负、平、得分率（胜为 1，平为 0.5，负为 0）、落子耗时中位数与 P95、搜索节点数、实际完成深度。按成对开局估计得分率差异的 95% 置信区间。

难度验收目标是中档对简单档、困难档对中档的得分率超过 50%，并有足够证据支持排序。若未达到，在参数冻结前调整配置，并用新的保留集合复测。

改进评估的实验结果如实报告，包括无提升或效果不稳定的情况。胜率与耗时数据由实际运行产生，不预设实验结论。
